Examples

examples/react-browser · examples/react-jsdom

The repository has two example projects with plain component tests, one in Vitest browser mode and one in jsdom. Their viewers show what describe-me makes of those tests.

Open the viewers #

React in browser mode

Vitest browser mode in Chromium, with tests that render through vitest-browser-react.

React in jsdom

jsdom with Testing Library and styled-components, shaped like a typical existing suite.

Note. The viewers are part of this site. On your machine, pnpm site builds them with the pages and serves everything at http://localhost:6060/. They do not open from disk. The viewer is a JavaScript module that fetches its data, and browsers allow neither over file://. Hosting the viewer has the details.

React in browser mode #

The project runs Vitest in browser mode with Playwright and Chromium, set up as in Getting started. Its tests import render from vitest-browser-react and interact through Locator methods and userEvent from vitest/browser. Nothing in them is written for describe-me apart from two calls to step().

examples/react-browser/src/Counter.test.tsx

import { render } from 'vitest-browser-react'
import { step } from '@describe-me/vitest'
import { Counter } from './Counter'

it('does not go below the minimum', async () => {
  const screen = await render(<Counter initial={1} />)
  await step('go down to the minimum', async () => {
    await screen.getByRole('button', { name: 'decrement' }).click()
  })
  // …assertions
})
Component What its tests show
Counter Every .click() on a Locator is a frame, so the second click shows the count at 2. step() names a frame after what it does: go down to the minimum.
Chip .click() on the remove button, with the click as its own frame.
SearchBox .fill() on a Locator, and userEvent.type and userEvent.keyboard, which type the query and submit it.
Menu userEvent.click opens the menu and userEvent.keyboard('{Escape}') closes it. In the second test a step() names the frame that opens the menu.
Button Variants, sizes and states. A rerender is a frame of its own: large, then small. userEvent.click with force: true clicks a loading button that swallows the click.
Postcard An imported image on a stylesheet url() background. The viewer serves both files long after the test ran. The caption is set in Lora, which previewHead loads.
StyledText Four lines, styled by an inline style, a <style> tag, a CSSOM insertRule and adoptedStyleSheets. All four colours survive.

The components import their CSS like app code does: styles.css, Chip.css and postcard.css. Every frame carries the styles the page had, see what is captured. previewHead in vitest.config.ts loads Inter from Google Fonts and Lora from a local fonts.css, the way an app shell would. See Fonts.

Naming.test.tsx renders components inside a context provider, from a test-local memo, inside a fragment, inside Suspense and after a rerender from an empty fragment. Each test is documented under the component it rendered, not the wrapper around it. One test, two environments lists the cases, and Naming explains the rules.

React in jsdom #

The project runs Vitest in jsdom with Testing Library and globals: true, set up as in Getting started. Its tests import render from @testing-library/react or from a custom render in src/test-utils.tsx. render is synchronous, and most tests have no await. Recording adds no act warnings, see jsdom.

The custom render wraps every test in a styled-components ThemeProvider and GlobalStyles, as many design systems do. It imports @testing-library/react itself, so its tests record without a change.

examples/react-jsdom/src/test-utils.tsx

function AllTheProviders({ children }: { children: ReactNode }) {
  return (
    <ThemeProvider theme={theme}>
      <GlobalStyles />
      {children}
    </ThemeProvider>
  )
}

function customRender(ui: ReactElement, options?: Omit<RenderOptions, 'wrapper'>) {
  return render(ui, { wrapper: AllTheProviders, ...options })
}
Component What its tests show
Heading A synchronous render through the test utils. The heading takes its colour from the theme.
Text Body copy and small muted copy, through the test utils.
Button Exported from PolymorphicButton.tsx. With component="a" it renders as a link. It is an anonymous generic forwardRef, documented under its export.
Badge A styled-components pill in two tones.
Panel A plain CSS import, the most common case.
Disclosure fireEvent.click opens it in one frame. user-event works as a setup instance, user.click, and through the direct API, userEvent.click, with one frame per click either way. A step() names close it again.
AsyncGreeting With the default eager render frame, the render frame shows the loader and the closing frame shows the greeting. See render frames.
Toast The file turns on fake timers and calls cleanup in afterEach. A fireEvent inside a step() dismisses it. After the timers advance, the closing frame shows the empty status region.
Postcard The same postcard as in browser mode. Here Postcard.tsx imports Lora's fonts.css like any stylesheet, and previewHead loads only Inter.
StyledText The same four lines as in browser mode. The adoptedStyleSheets line keeps its default colour, because jsdom has no constructable stylesheets.

Naming.test.tsx has the five cases of browser mode with its own components, plus one that renders through the test utils: Badge under the test-utils wrapper is documented as Badge, not as the ThemeProvider around it. See styled-components for how its styles reach the viewer.

Three test files render nothing the viewer can show, so they have no entry in it. They run like any other test. See what is left out.

  • use-toggle.test.tsx tests a hook with renderHook, which records no frames.
  • format-count.test.tsx tests pure logic.
  • act-environment.test.tsx checks that IS_REACT_ACT_ENVIRONMENT is set.

One test, two environments #

Some tests exist in both examples. Open them side by side to see what the environment changes.

Case Browser mode jsdom What differs
A photo on a patterned card Postcard Postcard Both look the same. Lora comes from previewHead in browser mode and from an imported fonts.css in jsdom.
Four style techniques StyledText StyledText The adoptedStyleSheets line is orange in browser mode only. jsdom has no constructable stylesheets.
Inside a provider Button variant=secondary Badge tone=danger A React context provider in browser mode, the styled-components ThemeProvider in jsdom.
From a test-local memo Chip tone=accent Badge tone=info Nothing but the component. Both skip the memo the test file defines.
Inside a fragment Button size=sm Text size=small jsdom renders through the test-utils wrapper, browser mode without one.
Inside Suspense Counter initial=2 Panel title=Suspended Browser mode puts the component straight inside Suspense. jsdom wraps it in a test-local component and gives Suspense a fallback.
After a rerender from an empty fragment Button variant=ghost Badge tone=danger Browser mode awaits rerender, jsdom calls it synchronously. Both show an empty first frame.

Choosing an environment weighs browser mode against jsdom.

Run them locally #

In a clone of the repository:

  1. Install pnpm install
  2. Build the packages pnpm build
  3. Install Chromium once, for browser mode: pnpm --filter react-browser exec playwright install chromium
  4. Run the browser-mode tests pnpm --filter react-browser test
  5. Run the jsdom tests pnpm --filter react-jsdom test
  6. Build and serve the site pnpm site, then open http://localhost:6060/examples.html.

To work on one example, run pnpm dev inside it. It runs vitest and describe-me dev side by side, so the viewer follows the tests as they rerun. See the CLI.
