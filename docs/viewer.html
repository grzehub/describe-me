Viewer and CLI

packages/viewer/cli · packages/viewer/src · vite.config.ts

describe-me dev serves the viewer, repaints it after every test run and can mount a test in Live. describe-me build writes the recorded frames as a static site, with Live under --live. This page covers both commands and everything the viewer does.

The CLI #

The describe-me package installs one binary. It always needs a command:

describe-me dev   [--data .describe-me] [--port 6006] [--no-live] [--root <dir>]
describe-me build [--data .describe-me] [--out describe-me-dist] [--no-vendor-fonts]
                  [--live] [--root <dir>]
Command or flag Default What it does
describe-me dev — Starts a Vite dev server for the viewer and serves the data directory under /__data. When the reporter rewrites manifest.json, the server tells the page, and the viewer loads the manifest again. Vite prints the URL. Then it starts the live preview and prints its address after Live preview:. It never downloads fonts.
describe-me build — Writes the viewer as a static site to --out and copies the data directory into it as __data/. With --live it builds the live preview into __live/ and writes __live.json next to the viewer. Then it downloads web fonts into the copy of the data (fonts in the static site). The data directory itself never changes.
describe-me --help — Prints the usage. So does describe-me without a command, also when it has flags.
--data .describe-me dev and build. The directory the reporter wrote, relative to the current directory. When you set the plugin's outDir, pass the same directory here.
--out describe-me-dist build only. Where the static site goes. The directory is emptied first, so never point it at a folder that holds other files.
--port 6006 dev only. The port of the dev server. When it is busy, Vite moves on to the next free port. Read the URL it prints.
--help, -h — Any command. Prints the usage instead of running it.
--live on in dev,
off in build		 build builds the live preview into the site, so the static site shows Live (Live in the static site). dev has it on anyway. The site then holds the compiled code of your components, the test files and the setup files with their test data, readable because it is not minified, and your project's public/. Publish it only where that code may be seen. A failed live build stops the command with exit code 1 (why it stops).
--no-live on in dev,
off in build		 dev starts the viewer alone, without the live preview. The Live toggle is then hidden. On build it is the default: the site has no Live.
--root from the manifest dev and build --live. The project of the live preview, relative to the current directory. Without it, the preview uses the root and configFile of the manifest. With it, the preview uses that directory and the config file Vitest picks there, the first vitest.config.*, then vite.config.*. Use it before the first test run, or when the manifest comes from another machine.
--no-vendor-fonts fonts are downloaded build only. Leaves web fonts on their hosts, so the build makes no network requests. Use it in CI without network access or under privacy rules.
  • Any first word other than build, a typo included, starts the dev server. Use --help for the usage.
  • A flag of the other command is ignored, so --port does nothing on build. Neither does --root without --live.
  • Without data, build warns no data at …; run vitest first and still finishes. The site then says "no manifest yet — run vitest first".
  • An unknown flag stops the CLI. It prints the error and exits with code 1:
describe-me: Unknown option '--prot'. To specify a positional argument starting with a '-', place it at the end of the command after '--', as in '-- "--prot"

Finding your way #

  • Header. The number of tests, how many passed and failed, the issues chip, the time of the last run and the theme switch.
  • Sidebar. The search field, then one block per test file with its describe blocks and tests in source order. A file with a single top-level describe shows its name over the file path. Each test shows its status, its tags and its number of frames. A click on a file or describe row opens its overview. The arrow in front of it collapses it. Drag the sidebar's right edge to make it narrower or wider, between 216 px and half the window. A window narrower than 592 px allows up to 296 px. A double-click on the edge sets it back to 296 px. Tab and ← → work too, as the keyboard table says. The browser keeps the width per project, like the collapsed rows. It is not part of the link. Without storage it lasts until you reload.
  • Stage. The test's path and the viewport toolbar with the Live toggle, the sizes and the background swatches, above the replayed frame or the test in Live. A note under a replayed frame names the fonts and stylesheets that did not load in your browser.
  • Frame timeline. One button per frame, with its kind, its label and the time into the test. A click shows that frame.
  • Inspector. The test's status and duration, the component with its props, the current frame as "frame 2 / 3" with its label, and the errors of a failed test. In Live, a Live section takes the place of the frame. Up to 12 props show in full. With more, the table shows the first 10 and Show N more, and Show fewer folds it again. It stays unfolded for that test, across frames and Live, until you reload the page.

The Counter increments test in the browser-mode example has three frames. Step through them with ← and →.

Theme

The three buttons at the right end of the header set the viewer's own colors. system, the default, follows your system. light and dark override it. The choice is the same for every project. The browser keeps it in localStorage, and it is not part of the link. Without storage the switch still works until you reload.

The theme never reaches a frame. A frame's canvas and color scheme come from the background switch alone, so a component looks the same in either theme.

Search and collapsing #

The field at the top of the sidebar filters the tests. Every word you type must occur, case-insensitive, in the test's full name with its suites, in its file path, in its component's name or in its tags. Different words may match different fields, so counter.test reset finds the Counter test that resets, by its file and its name. A search shows matches inside collapsed suites too. The search is not part of the link and is not stored.

A test's Vitest tags, its own and those of its describe blocks and file, show next to its name and in the inspector. A click on a tag in the inspector narrows the sidebar to the tests with that tag, and a second click shows every test again, as does the × next to the tag above the tree. The tag is part of the link, and ↑ ↓ follow it like the search. docs and no-docs do not show, because they only pick which tests become stories.

The arrow in front of a file or describe row collapses it. The browser keeps the collapsed rows in localStorage, per project, so several projects on localhost:6006 do not mix. Without storage, as in a private window that blocks it, collapsing still works until you reload. Opening a test expands the rows around it.

Keyboard #

Key Where What it does
← → a test The previous or next frame. In Live, they leave Live and show the frame that was selected before.
↑ ↓ a test The previous or next test the sidebar shows, so they follow the search and skip collapsed suites. From a test hidden in a collapsed suite, they go to the nearest row the sidebar shows. From a test the search does not match, ↓ goes to the first match and ↑ to the last.
↑ ↓ an overview ↓ opens its first test, ↑ its last.
L a test Turns Live on or off, once the live preview is ready. Either case, and not with Ctrl, Meta or Alt held.
/ anywhere Focuses the search and selects its text. Not with Ctrl, Meta or Alt held, which leaves the key to the browser.
Esc the search field Clears the search and leaves the field.
Enter ↓ the search field Opens the first match and leaves the field, so the arrow keys work again.
← → the sidebar's edge Narrows or widens the sidebar by 16 px. Tab reaches the edge after the sidebar's rows.

Shortcuts are off while you type in an input, a textarea, a select or an editable element, and until the manifest has loaded. They are also off while the sidebar's edge has focus. While the frame of a test in Live has focus, keys go to the component, as Live explains.

Viewport size and background #

The toolbar above the stage sets the size of the replayed page in CSS pixels, and what the frame stands on. The presets are 100%, 768px and 375px. The W and H fields take any width and height.

  • Sizes are whole numbers up to 10000. W starts at 1 and H at 120. A smaller H is raised to 120. Anything else, an empty field included, means auto.
  • An auto width fills the stage. 100% is the auto width.
  • An auto height fits what the frame paints, at least 120 pixels, and is measured again once the web fonts have loaded. Content sized to the viewport, such as a full-height layout or a dialog on a backdrop, gets the height of the stage. A dialog taller than the stage gets room for all of it.
  • A viewport wider than the stage is scaled down to fit, and the toolbar shows the zoom, such as 52%.

Background

Frames have no card. A frame shows only what its page's CSS paints, on the stage's canvas. The swatches after the presets pick the canvas:

  • light and dark set the canvas and the frame's color scheme. Under dark, prefers-color-scheme: dark matches inside the frame, so the component shows its own dark rules.
  • transparent is a checkerboard, with a light color scheme.
  • auto, the default, is light unless the recorded page declares a dark scheme on its root or paints its html or body dark. It never follows the viewer's theme or your system.
  • A page that sets its own color-scheme keeps it.
  • The overview's thumbnails follow the choice. It is part of the link as bg and is not stored.

Both examples paint their page white, so their frames show as a white sheet on the dark and transparent canvases, as in this Disclosure test of the jsdom example.

Live #

Live mounts the selected test for real, in a frame of the live preview, in place of its recorded frame. The component starts as the test's arrange phase set it up: everything before the test's first render runs, and nothing after it. So Live is a fresh start: it does not replay the test's interactions to reach a later frame. Writing stories explains which part of a test runs.

Opening it

  • The Live toggle, the first button of the viewport toolbar.
  • L in a test, as the keyboard table says.
  • live=1 in the link. Until the live preview is ready the recorded frame shows, then Live takes over. Try it on the Menu test of the browser-mode example: open Actions and pick Rename.

While it mounts

  • Until the live page reports a status, the recorded frame stays under the live frame, dimmed, with a shimmer. The Live label shows from the start.
  • With no recorded frame of the test on the stage, the shimmer runs on the empty canvas. That happens after Restart of a mounted test, after picking another test in Live, and with a live=1 link that opens Live before the frame shows.
  • The dot of the Live toggle pulses, and the inspector says "mounting…".
  • Any status ends it, one that went wrong too. The live frame fades in and the recorded frame fades out.
  • With prefers-reduced-motion: reduce there is no shimmer and no fade, and the toggle's dot is dim instead of pulsing.

What is real

  • Clicks, typing, timers and time are real.
  • Each call of a vi.fn() prop shows as an action under the prop's name, such as onSelect("Rename").
  • Errors the component throws show in the inspector.

The inspector

While Live shows, a Live section takes the place of the frame section:

  • A status dot and words, such as "mounted as the test arranged it". Troubleshooting explains each status.
  • Restart mounts the test again from a fresh start and clears the lists.
  • The detail of a status that went wrong, in red.
  • Actions, the calls of vi.fn() props, oldest first. It keeps the last 50.
  • Errors, the last 20 errors of the component.
  • Notices, the last 20 notices of the live page. Each vi.mock or vi.doMock call sends one, because the page loads the real module.

The component section shows the props the test rendered with. Once the live preview is ready, the keyboard hint at the bottom adds L live.

Size and focus

  • A Live label above the frame sets it apart from a recorded one.
  • The toolbar's presets, W, H and the background apply without reloading the frame, so the component keeps its state.
  • Under auto, Live keeps the canvas of the last recorded frame the stage showed, because the viewer does not read the live page.
  • The auto height follows the height of the content, but stops at the visible height of the stage. Taller content scrolls inside the frame. An explicit H wins.
  • Keys you press while the frame has focus go to the component, not to the viewer. Click outside the frame to use the viewer's keys again.

Moving around

  • ← and → leave Live and show the frame that was selected before. A click on a frame of the timeline leaves Live and shows that frame.
  • ↑ and ↓ keep Live and mount the previous or next test. So do a click in the sidebar, Enter in the search and a test in the issues list.
  • An overview and its gallery never show Live. Back in the test, the same frame shows, with its state. A thumbnail of the gallery opens its recorded frame, not Live.

When the toggle is hidden or greyed out

  • Hidden when the live preview is off: under --no-live, with live: false in the project's config, and on a static site built without --live.
  • Greyed out while the live preview starts, with the tooltip "The live preview is starting".
  • Greyed out when the live preview did not start. The tooltip then gives the reason, which the CLI also prints as describe-me: <reason>. Troubleshooting lists the reasons and their fixes.

The viewer never waits for the live preview, so the recorded frames show while it starts.

Where it runs

The live preview is a second Vite dev server, on your project's own Vite and config. It loads the project and config of the manifest, or of --root. describe-me dev starts it on a free port on localhost and prints its address, such as http://localhost:5173/__describe-me/. The viewer learns its state from /__live.json on its own dev server: starting, ready with the preview's base, off, or error with the reason. On a static site built with --live, the page is a static build under __live/, and __live.json next to the viewer says ready with that base (Live in the static site).

Links #

The address holds the view, so you can copy it to share a frame at a size:

#test=a7f4d7422f6a&frame=1&w=375
  • test is the test's id, frame counts from 0, and w and h are the viewport size. frame=1 is the inspector's "frame 2". The link leaves out frame 0 and an auto size.
  • suite takes the place of test for an overview.
  • bg is the background: light, dark or transparent. The link leaves out auto.
  • live=1 opens the test in Live, so it needs test. Until the live preview is ready, the recorded frame shows.
  • tag narrows the sidebar to the tests with that tag. Without test, the first of them opens. Setting or clearing it adds a history entry.
  • Opening a test or an overview adds a history entry, so Back and Forward move between them. Stepping through frames, moving with ↑ ↓, turning Live on or off and changing the size or the background replace the current entry.
  • A test id stays the same on other machines and when other tests are added, removed or reordered. Renaming a test or moving it to another suite or file changes it. A link to a test that no longer exists opens the first test.
  • A link written by 0.4 holds Vitest's own test id. It still opens its test, and the viewer rewrites the address.

That link opens the second frame of a Disclosure test in the jsdom example, 375 pixels wide.

Component overview #

A click on a file or describe row in the sidebar opens its overview. It shows the props of each component its tests render, which values the tests cover, and the last frame of every test as a thumbnail. Try the Button overview in the browser-mode example. Writing stories explains how coverage is counted. A long props table folds as in the inspector and stays unfolded for that component until you reload the page.

Issues and the version banner #

The issues chip in the header counts what this run could not document: setup problems, anonymous components, components without props docs, missing assets, fonts that nothing loads and remote stylesheet hosts. It opens a list with links to the tests, with setup warnings first, in a section of their own. When there is nothing to report, the chip is not there. Troubleshooting explains each entry.

The manifest names the describe-me release that wrote it. When its major.minor differs from the viewer's own, a banner under the header says so, for example: 

Written by @describe-me/vitest 0.6.0. This viewer is describe-me 0.5.2, so frames may not show correctly. Install every describe-me package at the same version.

The versions in it are those of your packages. Data from 0.5.0 and older names no writer and never shows the banner. Upgrade describe-me and @describe-me/vitest together, run the tests again and reload (one version for all packages). How it works explains which versions read which data.

Hosting the static site #

describe-me build writes plain files: the viewer, its assets and __data/. Any static file server or host can serve them.

  • Any sub-path. Every URL in the site is relative, the data included, so it works at /docs/ or under a GitHub Pages project path as well as at the root.
  • No rewrites. The view lives in the part after #, so the server only ever serves index.html and files.
  • Not from disk. The viewer is a module script that fetches its data, which browsers do not allow from file://. Serve the folder, even to look at it locally: 
python3 -m http.server 8080 --directory describe-me-dist

Then open http://localhost:8080/. An open page checks the manifest every 60 seconds and repaints only when a new run has been deployed.

Build the docs in CI has a GitHub Actions workflow that runs the tests, builds the site and publishes it to GitHub Pages.

Live in the static site

describe-me build --live puts the live preview next to the viewer, as __live/ and __live.json. Live then works as it does under describe-me dev:

  • Same origin. The viewer frames __live/live.html from its own origin, and the page posts its messages to that origin only.
  • Any sub-path. __live.json names the base __live/, relative to itself, and the live page uses relative URLs too.
  • Only with __live.json. A site built without --live has neither file, and the toggle stays hidden.
  • Your code is in it. The site holds the compiled code of your components, the test files and the setup files with their test data, unminified. Publish it only where that code may be seen.
  • Fonts load from their hosts. The live page links the remote stylesheets of the previewHead as they are, because font vendoring covers the recorded frames only.
